## 2. Формат сотрудничества

Основной режим Codex: MENTOR.

- Разработчик самостоятельно пишет основной код.
- Codex объясняет, направляет и помогает принимать решения.
- Подсказки выдаются постепенно.
- После реализации текущего задания проводится REVIEW.
- IMPLEMENT используется только по прямому разрешению.
- Одновременно выполняется одно учебное задание.
- Изменения файлов, установка зависимостей, команды проверки,
  Git-операции и deployment требуют разрешения.

Подробные правила находятся в AGENTS.md.

Ускоренный режим от 2026-10-15: пользователь сообщил, что до хакатона
остались сутки, и попросил воспроизводить реализацию последнего коммита MVP.
Пользователь сам вносит код и запускает команды; Codex даёт готовые фрагменты,
объясняет устройство и проверяет результат по запросу. Показ готового кода
явно разрешён. Самостоятельное изменение исходников Codex не разрешено;
прежнее разрешение на ведение PROJECT_CONTEXT.md сохраняется.
Работать проверяемыми модулями с кратким разбором для самостоятельного
объяснения архитектуры и кода. Происхождение используемого кода не скрывать.

### Разделение ответственности

Пользователь работает над всем приложением вместе с Codex.
2026-10-15 он взял на себя и frontend, чтобы не зависеть от напарника.
Прежнее разделение на исполнителей больше не ограничивает задания:
воспроизводим всю реализацию MVP, включая интерфейс.

| Ответственный | Область |
| --- | --- |
| Пользователь + Codex | Express/Socket.IO backend, комнаты, права участников, каталог, загрузки и аудиофайлы на диске, HTTP с Range |
| Пользователь + Codex | Общие TypeScript-типы, Zod-схемы, контракты событий, ID, данные приглашений и QR |
| Пользователь + Codex | Браузерная аудиологика: HTMLAudioElement, готовность к старту, оценка часов, расписание воспроизведения, коррекция drift, reconnect и сетевая интеграция |
| Пользователь + Codex | Vitest, Playwright, ESLint/typecheck, Git/GitHub Actions, Linux, Docker Compose, Caddy, HTTPS/WSS |
| Пользователь + Codex | Страницы, визуальные компоненты, CSS, адаптивность, отображение состояний и подключение технических модулей к интерфейсу |

Пользователь явно подтвердил, что браузерную аудиологику пишем мы с ним:
она выполняется в apps/web и остаётся в нашей области ответственности.
Теперь пользователю можно назначать и задания по визуальной вёрстке.

Граница интеграции — согласованные данные и действия. UI вызывает действия
технического модуля и отображает его состояние. Серверные проверки прав
и валидация обязательны независимо от доступности кнопок в интерфейсе.
Контракты между модулями фиксируются в общем пакете до интеграции.
Отдельные задания напарнику больше не нужны; раньше сообщений ему
из этого чата не отправляли, его фактический прогресс неизвестен.

## 5. План архитектуры

apps/web:
- страницы, интерфейс и отображение состояний — пользователь + Codex;
- подключение к комнате и состояние сетевого клиента — наша часть;
- управление HTMLAudioElement, синхронизация и локальная громкость
  как технические действия — наша часть;
- визуальное представление плеера, приглашений и участников — пользователь + Codex.

apps/server:
- HTTP API;
- Socket.IO transport;
- RoomManager;
- SyncEngine;
- локальный музыкальный каталог;
- обработка загрузок.

packages/shared:
- общие TypeScript-типы;
- контракты сетевых событий;
- схемы Zod.

Основные принципы:

- Сервер является источником состояния комнаты.
- RoomManager не зависит от Socket.IO transport.
- Комнаты хранятся в Map одного backend-процесса.
- База данных для первого MVP не требуется.
- Аудиофайлы передаются по HTTP с поддержкой Range.
- Аудиофайлы хранятся на диске; комнаты — в памяти процесса.
- Socket.IO передаёт команды, timestamps и состояние.
- Сетевые входные данные валидируются через Zod.
- Управление playback требует проверки membership и роли HOST.
- Revision защищает от устаревших сообщений.
- После reconnect клиент получает актуальный snapshot.

Это план новой реализации, а не перечень уже написанных модулей.

## 7. Требования к синхронизации

Клиенты используют собственные HTMLAudioElement.

План алгоритма:
- NTP-подобная оценка разницы часов по нескольким измерениям;
- учёт RTT и предпочтение измерений с меньшей задержкой;
- общий серверный timestamp начала воспроизведения;
- подтверждение буфера и разрешения звука;
- вычисление ожидаемой позиции из серверного anchor;
- ограниченная коррекция playbackRate при умеренном drift;
- коррекция currentTime при большой ошибке;
- обработка паузы, seek, конца трека и reconnect.

Браузер может запрещать autoplay.
Каждый слушатель должен активировать звук пользовательским жестом.

Drift означает оценку ошибки медиапозиции.
Он не доказывает точную синхронность физического звука
на динамиках или Bluetooth-наушниках.

## 8. Внешние музыкальные сервисы

«Звук» рассматривается как отдельная будущая интеграция.
Он не должен становиться обязательной зависимостью Local Music.

Авторизация через Сбер ID сама по себе не даёт
доступ к музыкальному каталогу или воспроизведению.

Интеграция допускается только при проверенном
и разрешённом механизме доступа.
При отсутствии разрешённого playback API нужен
честный статус UNSUPPORTED.

Запрещены обход DRM, извлечение чужих токенов,
обход подписки и передача подписного аудио другим пользователям.

Интеграция не является текущим учебным заданием.
