# Алгоритм синхронизации SYNC

Обновлено 2026-10-14. Протокол v4. Backend, web и shared нужно обновлять вместе.
Хранилище комнат — Map одного процесса; аудио передаётся по HTTP с Range.
Socket.IO передаёт состояния, подтверждения готовности, команды и временные отметки.

## Источник состояния

RoomManager проверяет membership и expectedRevision перед каждой командой. Play/seek/track
доступны HOST; Pause доступна любому активному участнику.
`trackRevision` — revision последнего выбора/очистки трека (включая повторный выбор того же ID).
Готовность привязана к этой версии. Readiness-состояние участника включено в snapshots.
Клиент отдельно запоминает revision последнего полного snapshot. Если новый player:state
пришёл раньше snapshot с предыдущей revision, snapshot ещё может обновить участников/HOST,
но его старые поля timeline не заменяют новые. Более старые полные snapshots игнорируются.
Серверные часы timeline и clock pong используют один монотонно ограниченный источник:
при переводе wall clock назад уже установленное серверное время не уменьшается.

`SyncEngine` — чистый модуль shared, также доступный через server/sync. Формула:

```text
playing: expected = min(duration, anchorPosition + max(0, serverNow − startedAt) / 1000)
paused:  expected = min(duration, anchorPosition)
```

Если startedAt в будущем, позиция остаётся на anchorPosition до общего старта.
Чтение snapshot не сдвигает anchor. Смена трека ставит паузу, позицию 0 и новую trackRevision.
Seek во время playing задаёт position и startedAt=serverNow, чтобы задержавшийся клиент
сразу вычислил пройденное после команды время. Pause фиксирует вычисленную позицию;
pause до будущего старта отменяет его без добавления времени.

## ClockOffsetEstimator

Клиент записывает t0 (отправка), сервер — t1 (приём) и t2 (отправка), клиент — t3 (приём).
Дополнительно клиент фиксирует performance.now при отправке и приёме.
Формулы заимствуют принцип [четырёх отметок NTP](https://www.rfc-editor.org/rfc/rfc5905.html#section-8):

```text
RTT = (t3 − t0) − (t2 − t1)
offset = ((t1 − t0) + (t2 − t3)) / 2
serverNow = serverAnchor + (performance.now() − monotonicAnchor)
```

Это NTP-подобный обмен поверх Socket.IO, не реализация полного NTPv4.
При входе/reconnect/возвращении во вкладку выполняется серия из 6 измерений с интервалом
60 мс. Первичная калибровка требует минимум 3 валидных измерения. Затем запрос повторяется
раз в 5 с. Хранятся максимум 16 образцов не старше 30 с. Отсутствие успешного обмена 15 с
делает часы неготовыми. Отрицательный RTT, RTT > 2 с и неправильный порядок timestamps отбрасываются.

Выбираются образцы с RTT не выше minRTT + max(5 мс, 25% minRTT), затем рассчитывается
взвешенный offset с весом `1 / (1 + RTT)^2`. Медленные образцы не перетягивают оценку.
Разница wall-time elapsed и monotonic elapsed > 25 мс означает скачок клиентских часов:
образцы сбрасываются. Скачок wall clock между обменами > 100 мс тоже сбрасывает старую оценку.
Дальнейшая проекция использует performance.now, поэтому перевод клиентских часов между
измерениями не меняет позицию звука мгновенно. После сброса нужна новая калибровка.
До калибровки шкала UI приближённо проецируется от последнего server timestamp из snapshot;
задержка его доставки ещё не компенсирована, drift не показывается и audio не запускается.

Симметрия сети — допущение. Asymmetric delay, очереди TCP и браузера могут смещать offset.
Показанный RTT — время обмена, не гарантированная точность часов или звукового выхода.

## Buffer readiness и autoplay

Перед PLAY каждый активный участник должен подтвердить текущий трек:

```ts
player:ready {
  roomId, trackId, trackRevision, sequence,
  status, bufferedSeconds, soundUnlocked, clockSynced
}
```

Все поля проходят Zod. Ready требует `soundUnlocked=true`, `clockSynced=true` и положительный
bufferedSeconds. Клиент дополнительно проверяет тот же currentSrc, readyState >= HAVE_CURRENT_DATA,
и buffered TimeRanges: перед стартом минимум 0,75 с или весь оставшийся короткий фрагмент.
Во время playback проверяется фактический cursor декодера с порогом 0,12 с, чтобы оценка
серверного времени чуть за краем буфера не обрывала нативное воспроизведение.
При конце проверяется буфер в начале для последующего повторного PLAY.
Если браузер удалил начало из TimeRanges после перемотки к концу, тот же активированный
элемент беззвучно догружает начало. Scheduler оставляет серверную позицию на конце,
не перематывает декодер обратно к хвосту и не показывает priming как измеренный drift.
Количество bufferedSeconds в snapshot — последнее сообщение устройства, не непрерывный счётчик.

Кнопка «Включить звук / Готов слушать» вызывает play() непосредственно в обработчике жеста
на том же HTMLAudioElement. Только успешный promise подтверждает soundUnlocked. Пока идёт
проверка разрешения, server pause не обрывает этот promise; затем применяется актуальное состояние.
NotAllowedError снимает готовность и возвращает кнопку. Нельзя считать наличие метаданных
или успешное socket-подключение разрешением звука. Это согласуется с
[правилами autoplay браузеров](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay).

Контроллер устанавливается до появления доступной кнопки на экране (`useLayoutEffect`),
чтобы поздний passive effect не отменял первый play() после resume. Перезапуск привязан
к id/path/duration и trackRevision, а не к ссылке на объект метаданных. Успешный native
play() сразу подтверждает разрешение; догрузка буфера остаётся отдельным условием Ready.
Инициализация не стирает состояние или ошибку уже начатой попытки активации.

У приватного файла HTTP session/cookie проверяется до первого жеста: до ответа кнопка
Ready недоступна, UI пишет «Подключаем музыку комнаты». Это отдельный этап от preload;
загрузка буфера не блокирует кнопку после выдачи доступа. Отказ/timeout доступа показывает
явную ошибку и «Повторить подключение музыки». Первая активация после успешного подключения
не теряет жест из-за await HTTP. При уже сохранённом разрешении новый файл подключается автоматически.

Выбор нового трека снимает серверную готовность всех, но сохраняет подтверждённое разрешение
того же HTMLAudioElement в текущей вкладке. Новый файл автоматически прогревается без
звучания до общего PLAY; клиент вновь проверяет буфер и часы и сообщает новую trackRevision.
После конца трека и смены файла повторно нажимать «Готов слушать» не требуется.
Reload создаёт новый элемент и требует нового жеста. Сохранение одного элемента следует
[рекомендации WebKit о permission per element](https://webkit.org/blog/7734/auto-play-policy-changes-for-macos/);
это не обещание одинаковой политики всех версий Safari. При reconnect того же audio элемент сохраняет подтверждённое разрешение,
но сервер снимает readiness; заново проверяются буфер и часы. Разрешение нельзя сохранить в storage.
Нет способа сервером аттестовать физический звук браузера: сервер принимает проверенные по схеме
сообщения клиента о его наблюдаемом состоянии, а не утверждает наличие звука в динамиках.

Readiness reports идут при смене статуса и раз в 4 с. Сервер проверяет trackRevision и возрастающий
sequence, чтобы старое ready не заменило более новое blocked/buffering. Heartbeat без смены статуса
не увеличивает room revision. Через 15 с без свежего ready сервер ставит stale и публикует snapshot.
Состояния: loading, buffering, blocked, clock, ready, error, stale.

Обновление очереди/участников/библиотеки не пересоздаёт неизменившийся Track на клиенте:
это сохраняет жизненный цикл HTMLAudioElement и разрешение звука. Новая trackRevision
по-прежнему снимает готовность. Перед управляющим действием клиент завершает собственные
отчёты readiness и откладывает новые до ack команды; серверная проверка expectedRevision
остаётся строгой. Изменение другим участником может вернуть STALE_REVISION с новым snapshot.

Загрузка хранит фактическую длительность в `room.library`; сервер и scheduler используют
её при проекции позиции и завершении. При конце композиции непустая очередь выбирает
следующую и ставит паузу. Новый файл ждёт свежий буфер/часы всех слушателей и новый Play; уже выданное разрешение
на звук сохраняется. Реальный NotAllowedError возвращает кнопку активации.

## PlaybackScheduler

При PLAY RoomManager требует свежий ready всех активных участников. Иначе отвечает NOT_READY
без изменения timeline. Успешный PLAY назначает startedAt = serverNow + PLAY_LEAD_MS
(по умолчанию 750 мс; конфигурация 100–3000). Все получают один anchor и revision.

Каждый клиент переводит серверный deadline через ClockOffsetEstimator и ставит собственный
таймер. До deadline audio остаётся на паузе. Callback перечитывает актуальное состояние;
pause/seek/track/disconnect отменяют старый таймер. При поздней доставке или позднем входе
клиент не ждёт прошедший deadline, а выставляет вычисленную текущую позицию и догоняет timeline.
Поздний join не останавливает уже играющих: новый участник активирует звук и готовит буфер отдельно.

Входящие обновления room/clock/connection применяются через подписку без ожидания
100-мс контрольного интервала. Disconnect, ошибка файла или отзыв разрешения останавливают
локальное аудио с rate=1. Краткий waiting или clock expiry не обрывает уже запущенный
нативный decoder; новый PLAY всё равно требует свежего ready.
После восстановления подключения применяется позиция свежего snapshot даже при
небольшом накопленном разрыве; rate-коррекция используется для продолжающегося воспроизведения. Планировщик независим от React,
принимает MediaPort, источник времени и внедряемые таймеры. Старое состояние меньшей revision
не может восстановить отменённый старт. Уничтожение контроллера отменяет его callbacks.

## DriftCorrector

Ошибка временной позиции: `drift = audio.currentTime − expectedPosition`.
Оба значения реально прочитаны/вычислены в этой вкладке. Политика при playing:

| Абсолютная ошибка | Действие |
| --- | --- |
| <= 0,04 с | Не двигать currentTime; вернуть playbackRate к 1 |
| < 0,6 с | Rate стремится к `1 − drift × 0,1`, в диапазоне 0,99–1,01 |
| >= 0,6 с | Подтвердить устойчивую ошибку, затем currentTime = expected, rate=1 |

Rate меняется максимум на 0,002, не чаще одного раза за 200 мс. Целевая скорость округляется
до 0,001, чтобы шум оценки часов не вызывал постоянную перенастройку аудио. Частота событий
media/readiness/snapshot не ускоряет эту коррекцию: контрольный таймер и новые события могут
проверять состояние чаще, но не менять rate несколько раз за одну миллисекунду.
Неизменившийся rate не записывается повторно; совпадающая позиция не вызывает лишний seek.
При явном изменении anchor/track/seek позиция применяется немедленно,
без ожидания интервала rate-коррекции.
Первые 1,5 с после подтверждённого play() автоматическая коррекция отключена: скорость 1,
чтобы декодер успел начать стабильное воспроизведение. Явные seek/смена anchor
по-прежнему исправляются сразу. Поздний play promise уничтоженного контроллера
не может остановить элемент, уже используемый следующим треком.
Большая автоматическая коррекция требует ошибки одного знака не менее 800 мс после
стабилизации декодера; разрешена не чаще одного раза за 5 с. При pending play, seeking
или readyState < HAVE_FUTURE_DATA новые автоматические коррекции не запускаются.
После перемотки и после наблюдаемого завершения seeking даётся ещё 1,5 с на стабилизацию.
Новая серверная команда может сразу заменить старый seek. На pause положение корректируется
при ошибке > 0,03 с после завершения предыдущей перемотки; rate всегда возвращается к 1.
`drift` считывается до коррекции, поэтому запись нового currentTime не превращает оценку
мгновенно в ноль. Это показание браузерной timeline, не измерение динамиков.
Browser [playbackRate](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/playbackRate)
не является управлением задержкой физического аудиоустройства.

В адаптивном профиле устанавливается `preservesPitch=false`: небольшие корректировки используют
ресэмплинг вместо pitch-preserving time stretch. Chromium документирует [артефакты WSOLA и
переходов между rate=1 и соседними скоростями](https://chromium.googlesource.com/experimental/chromium/src/+/HEAD/media/filters/audio_renderer_algorithm.cc).
Это компромисс: во время коррекции темп и высота тона могут временно измениться максимум на 1%.
При ровном воспроизведении, паузе и после seek скорость равна 1. Аудиобайты на сервере не изменяются.

Позиция ограничена длительностью; сервер завершает трек и рассылает paused с новой revision.
Клиент не перезапускает уже ended аудио в последние 80 мс, пока ждёт серверное окончание.
При PLAY с конца сервер задаёт начало 0 и новый deadline. Смена трека и cleanup сбрасывают rate.

Браузер может тормозить таймеры в фоне: [Page Visibility](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API).
При возвращении запрашиваются snapshot и серия clock samples; apply немедленно проверяет timeline.
Скрытая вкладка не может обещать исполнение callback точно в deadline. Время аппаратного выхода,
декодер, Bluetooth, энергосбережение и асимметрия сети не измерены этим алгоритмом.

## Диагностический экран

В комнате есть ссылка на `/sync-lab`. Он использует тот же реальный плеер и backend.
Показывает expected/actual позиции, оценку drift, текущий playbackRate, режим коррекции,
время до scheduled start, clock offset/RTT, число измерений и revision.
После seek показаны обновлённые currentTime и соответствующий им drift.

Проверка: создайте комнату, войдите из второго браузерного профиля, откройте лабораторию
в каждом, включите звук, дождитесь ready и нажмите PLAY на HOST.
Поле задержки (0–5000 мс) откладывает входящие snapshots/player states и ack плеера только
в этой вкладке. Clock ping и HTTP-аудио не задерживаются. При смене задержки старые queued
события могут прийти позже новых — это позволяет наблюдать revision guard. При выходе с экрана
задержка сбрасывается; при disconnect callbacks старого соединения игнорируются.

Показанный drift — ошибка временной позиции HTMLAudioElement. Он **не равен** точной разнице
физического выхода звука из двух устройств. Нулевой drift не доказывает акустическую синхронность.

## Автоматическая проверка

- Unit: ClockOffsetEstimator, DriftCorrector, PlaybackScheduler, SyncEngine, readiness RoomManager.
- Socket.IO integration: общие PLAY/PAUSE/SEEK, snapshots, late join, disconnect/reconnect,
  track changes, права, readiness и старые версии/отчёты.
- Scheduler с fake timers: два клиента с разной задержкой доставки, общий deadline,
  отмена стартов, late delivery, изменение трека, корректировка drift и end.
- Playwright: настоящие HTTP-аудио и два Chromium-контекста, clock skew +9000 мс,
  задержанные/переупорядоченные события, измерение currentTime/rate, autoplay denial,
  reload и desktop/mobile интерфейс. Допуск в тестах относится только к наблюдаемой timeline.

Сквозной final-audit.spec.ts использует два независимых BrowserContext с отдельным storage,
декодирует показанный QR и сравнивает полученные server snapshots/playback anchors той же revision.
Закрытие реального WebSocket проверяет локальную паузу; изменения трека/очереди во время
отключения проверяются после resume прежнего participantId. Wire observer подключается к
настоящему серверу, не подменяет состояние и не сохраняет private ACK.
Обнаружение физического обрыва сети зависит от transport heartbeat; оно не гарантированно мгновенное.

Readiness другого участника может изменить revision между нажатием и доставкой Seek/Pause,
особенно на WAN. Сервер правильно отклоняет такую команду; UI запрашивает snapshot и предлагает
новое действие. Автотест следует этому предложению только после явного STALE_REVISION,
не убирает guard и не делает silent retry в приложении.

## Аудиопрофиль Apple и восстановление вывода

Safari и браузеры iPhone/iPad используют native-профиль: playbackRate=1, штатный preservesPitch, без постоянной дробной коррекции скорости. Устойчивая большая ошибка исправляется через currentTime. Chromium и Firefox вне iOS используют адаптивную коррекцию. Это сохраняет поведение эталона и не является измерением физической слышимости.

Один HTMLAudioElement переиспользуется при смене трека и reconnect. Ready запускает native play в пользовательском жесте, проверяет буфер и продвижение currentTime. Reload или отказ autoplay требуют нового жеста. Диагностика и восстановление звука доступны в интерфейсе. Акустическую синхронность на физических устройствах проверяют отдельным прослушиванием.
